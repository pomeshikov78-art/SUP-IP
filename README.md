# СУП-ИП — система управления проектами инженерного подразделения

**Версия 1.11.0 · клиент-серверная реализация по ТТ-2 (редакция ТЗ 3.0)**

Автономная многопользовательская система для локальной сети: сервер на Python 3 + **PostgreSQL**,
веб-клиенты в браузере без установки. Все 18 модулей M00–M17, серверная проверка прав на каждую
операцию, централизованный аудит, версионирование документов с файловым хранилищем, инженерные
расчёты, резервное копирование и восстановление, HTTPS, серверный центр уведомлений
и напоминаний с планировщиком.

| Способ | Когда выбирать |
|---|---|
| **Скачать и установить автоматически** | есть интернет; установщик сам загружает PostgreSQL 16 (~350 МБ) и ставит его тихо |

## 1. Архитектура (ТЗ §2, трёхуровневая)

| Уровень | Реализация |
|---|---|
| **1. Единое ядро** | `server.py`: PostgreSQL (пул соединений), REST/JSON API, сессии, матрица прав (проверка на сервере при каждой операции), журнал событий (AUDIT / BUSINESS / TECH / SECURITY / INTEGRATION), файловое хранилище `data/files`, резервирование, планировщик уведомлений и напоминаний |
| **2. Функциональные модули** | M00–M17: портфель, задачи, канбан, Гант, ресурсы, трудозатраты, контроль отклонений, риски, документы, расчёты, аналитика, календарь, отчёты, администрирование, журнал, совещания, конструктор дашбордов |
| **3. Веб-интерфейс** | `static/index.html` — SPA без внешних зависимостей и CDN (полная автономность, ТЗ §8). Клиент — представление данных; все мутации выполняются сервером |

**Принцип владения данными:** единственный владелец — серверная БД PostgreSQL. Клиент получает
снимок состояния (`/api/state`), отправляет операции (`/api/rpc`), сервер проверяет права,
валидирует данные, применяет изменение и пишет аудит **в одной транзакции**, затем возвращает
новое состояние. Другие клиенты получают изменения поллингом (~12 с). Производная аналитика
(прогресс, здоровье проектов, отклонения, графики, HTML-отчёты) вычисляется клиентом из единого
состояния; снимок отчёта сохраняется на сервере (M13).

## 2. Требования

- **Сервер:** Windows 10/11 x64 (или Linux), Python 3.10+, **PostgreSQL 14+** (рекомендуется 15/16).
- **Клиенты:** любой современный браузер в ЛВС (Chrome, Edge, Firefox). Установка не требуется.
- **Сеть:** изолированная ЛВС, интернет не нужен (ТЗ §8). До **10 одновременных пользователей** (ТЗ §2).
- SQLite **не используется**: ТЗ §4.1 прямо запрещает её как равнозначную замену PostgreSQL
  в многопользовательском режиме.

## 3. Установка одним EXE (рекомендуется, ТЗ §7)

Готовые файлы собираются автоматически в GitHub Actions — сценарий сборки
[`tools/github/build.yml`](tools/github/build.yml): сначала интеграционные испытания API на
PostgreSQL, затем сборка `SUP-IP.exe` (PyInstaller) и установщика (NSIS). Результат —
**Releases** (по тегу `vX.Y.Z`) и артефакт `SUP-IP-windows-x64` на вкладке Actions.

Автосборка включена: сценарий лежит в `.github/workflows/build.yml` и запускается при каждом
пуше в `main` и при публикации тега версии. Установщик собирается NSIS на Linux-раннере
(`makensis` формирует Windows-инсталлятор и вне Windows) — это исключает зависимость от
Chocolatey и внешних репозиториев на раннере. Сборка `SUP-IP.exe` и его самотестирование
выполняются на `windows-latest`.

- **`SUP-IP-Setup-x.y.z.exe`** — единый установщик: проверка Windows 10/11 x64 и диска → выбор
  каталога → **страница PostgreSQL** (автозагрузка / офлайн-файл / существующий сервер) →
  параметры (пароль PostgreSQL, порт, пароль администратора, HTTPS) → распаковка →
  подготовка СУБД и ожидание её готовности → схема и демо-данные → самоподписанный сертификат
  HTTPS → **служба Windows с автозапуском и автоперезапуском** → правило брандмауэра → проверка
  работоспособности → отчёт `data\install-report.txt` и журнал `data\logs\installer.log`.
- **`SUP-IP.exe`** — самодостаточный сервер (Python и веб-клиент внутри).Режимы:
  - `SUP-IP.exe --install` — интерактивный мастер установки и настройки;
  - `SUP-IP.exe --install-auto params.ini` — автоматическая настройка (используется установщиком);
  - `SUP-IP.exe --service install|start|stop|restart|remove` — служба Windows;
  - `SUP-IP.exe --health` — диагностика (БД, файловое хранилище, порт);
  - `SUP-IP.exe --backup-now` — резервная копия в `data\backups`;
  - `SUP-IP.exe --migrate` — миграции БД при обновлении;
  - `SUP-IP.exe --version` — версия сборки;
  - `SUP-IP.exe --selftest` — проверка целостности поставки без БД (клиент, зависимости, шрифты, каталог данных);
  - `--log-level LEVEL`, `--log-dir DIR` — уровень и каталог файловых журналов (см. §7в).

Консольные режимы (`--install`, `--health`, `--selftest`, `--version`) принудительно переводят
консоль Windows в UTF-8: без этого штатная кодовая страница cp1252 не кодирует кириллицу и
мастер установки завершался бы ошибкой `UnicodeEncodeError`.

**Журнал установщика ведётся в единой кодировке UTF-16LE** (с меткой порядка байтов), вывод
всех команд попадает в журнал целиком — подробности и разбор типовых отказов в §7з.
**Офлайн-пакет имеет приоритет:** если PostgreSQL включён в установщик
(`SUP-IP-Setup-full.exe`), загрузка из сети не выполняется ни при каком положении
переключателей (ТЗ §8 — автономность).

**Обновление** (§7.6): новый Setup поверх установленного — автоматически: резервная копия →
остановка службы → замена файлов → миграции БД → запуск → проверка. Откат — восстановлением
копии из `data\backups` (M14 → Восстановить). **Деинсталляция** (§7.7): данные сохраняются по
умолчанию; удаление данных — только явным подтверждением.

**Полностью офлайн-пакет**: `SUP-IP-Setup-full-x.y.z.exe` собирается автосборкой при каждом
теге версии — PostgreSQL 16 включён внутрь и ставится тихо без интернета. Для собственной
сборки положите `postgresql-16.x-windows-x64.exe` как `sup-ip/installer/postgresql-setup.exe`
перед `makensis` (или запустите workflow с `bundle_postgres=true`).

Конфигурация после установки — `supip.ini` рядом с EXE (порт, DSN, сертификат); параметры
командной строки имеют приоритет.

### Сборка установщика на своём Windows-ПК

```bat
sup-ip\installer\build_installer.bat
```
(нужны Python 3.10+ и NSIS; результат — `dist\SUP-IP.exe` и `dist\SUP-IP-Setup-x.y.z.exe`).
Скрипт установщика проверяется компиляцией `makensis installer/setup.nsi` (в т.ч. на Linux),
поэтому ошибки сценария установки выявляются до выпуска сборки.

## 3а. Ручная установка (альтернатива)

1. **PostgreSQL.** Установите PostgreSQL 15/16 с официального установщика (offline). Запомните
   пароль суперпользователя `postgres`. Служба запускается автоматически.
2. **БД и роль.** В `psql` (меню «Пуск → SQL Shell») выполните **по отдельности**:
   ```sql
   CREATE USER supip PASSWORD 'supip';
   CREATE DATABASE supip OWNER supip;
   ```
   (или через pgAdmin). При других имени/пароле — передайте `--dsn` серверу, см. ниже.
3. **Python.** Установите Python 3.10+ (галочка «Add to PATH»), затем:
   ```bat
   python -m pip install psycopg2-binary
   ```
   Для полностью офлайн-установки заранее скачайте wheel: `pip download psycopg2-binary -d wheels`,
   перенесите папку и ставьте `pip install --no-index --find-links wheels psycopg2-binary`.
4. **Запуск.** Дважды щёлкните `run.bat` (или `python server.py --port 8000`).
   При первом запуске сервер создаёт схему и эталонный демо-набор (идемпотентно).
5. **Клиенты.** Откройте `http://<IP-сервера>:8000` в браузере. Брандмауэр Windows: разрешите
   входящий TCP-порт 8000 для профиля «Частная сеть».

### Демо-доступы

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | demo | Администратор |
| `morozov` | demo | Руководитель подразделения |
| `volkova`, `lebedev` | demo | Руководители проектов |
| `novikov`, `kozlova`, `orlov` | demo | Исполнители |
| `zaytseva` | demo | Наблюдатель |

Пароль меняется в профиле (кнопка «Сменить пароль»); администратор может сбросить пароль в M14.
3 неудачные попытки входа блокируют учётку на 60 с; неактивная сессия завершается через
`sessionMin` (M14, по умолчанию 60 мин). Все входы/отказы — категория SECURITY в M15.

### Параметры командной строки

```
python server.py [--host 0.0.0.0] [--port 8000]
                 [--dsn "host=127.0.0.1 port=5432 dbname=supip user=supip password=supip"]
                 [--cert cert.pem --key key.pem]   # HTTPS
                 [--no-seed]                       # не заполнять демо-данные
```
Переменные окружения: `SUPIP_PORT`, `SUPIP_DSN`.

### HTTPS (ТЗ §7)

Сгенерируйте самоподписанный сертификат для имени сервера (openssl есть в комплекте Git/PostgreSQL):
```bat
openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 825 -subj "/CN=supip-server"
python server.py --cert cert.pem --key key.pem
```
Клиенты открывают `https://<IP>:8000` (для самоподписанного сертификата добавьте исключение
или распространите сертификат в доверенные корневые средствами Windows). Cookie сессии
получает флаг `Secure`.

### Автозапуск как службы Windows

Рекомендуется [NSSM](https://nssm.cc) (offline-утилита):
```bat
nssm install SUP-IP "C:\sup-ip\SUP-IP.exe" "--port 8000"
nssm set SUP-IP AppDirectory C:\sup-ip
nssm start SUP-IP
```

## 4. Автономный EXE (Windows x64)

На машине с Python выполните `build_exe.bat` (ставит PyInstaller и собирает один файл):
```bat
python -m pip install pyinstaller psycopg2-binary
pyinstaller --onefile --name SUP-IP --add-data "static;static" server.py
```
Результат `dist\SUP-IP.exe` (~15–20 МБ) содержит сервер и веб-клиент; переносится на целевой ПК
без Python. **PostgreSQL устанавливается отдельно** (требование ТЗ §4.1) — EXE подключается к нему
по `--dsn`. Каталог `data/` создаётся рядом с EXE.

## 6. Резервное копирование и восстановление (M14)

- **Копия:** M14 → Система → «Резервная копия (JSON)» (или `GET /api/backup` под администратором):
  консистентный JSON-дамп всех 16 таблиц, включая пользователей, журнал, уведомления,
  напоминания и связи решений с поручениями. Событие TECH в M15.
- **Восстановление:** «Восстановить» → выбрать JSON-копию: данные полностью заменяются в одной
  транзакции, все клиенты получают новое состояние; событие SECURITY в M15.
- **Совместимость:** копии прежних версий (13 таблиц до v1.4.0, 15 — до v1.6.0) восстанавливаются —
  отсутствующие таблицы уведомлений, напоминаний и связей поручений считаются пустыми.
- **Файлы документов** хранятся в `data/files` — включайте этот каталог в файловые бэкапы.
- Для регулярных копий используйте планировщик Windows + `pg_dump`:
  ```bat
  "C:\Program Files\PostgreSQL\16\bin\pg_dump.exe" -U supip -h 127.0.0.1 -Fc supip > backup_%date%.dump
  ```
- «Сброс демо-данных» пересоздаёт эталонный набор (необратимо, подтверждение + аудит).

## 7. Безопасность (ТЗ §7)

- Пароли: PBKDF2-SHA256, 150 000 итераций, индивидуальная соль; в БД только соль+хеш.
- Сессии: случайный токен 192 бит, cookie `HttpOnly; SameSite=Lax` (+`Secure` при HTTPS),
  idle-таймаут, лимит 10 одновременных пользователей, принудительное завершение при блокировке.
- **Каждая** операция проходит серверную проверку прав (роль × модуль × действие + объектный
  уровень: РП — только свои проекты, исполнитель — только свои задачи/часы). Отказ → HTTP 403
  + событие SECURITY. Матрица прав настраивается в M14 и применяется немедленно.
- SQL — только параметризованные запросы; загрузка файлов — с проверкой прав и лимита 25 МБ.
- Клиентские события журналируются лишь в категориях TECH/INTEGRATION/AUDIT; BUSINESS и
  SECURITY пишет только сервер (подделка записей журнала клиентом невозможна).

## 7а. Документы: DOCX, XLSX, PDF, CSV, HTML (ТЗ §25)

Все документы формирует **сервер** (`docgen.py`, только стандартная библиотека Python —
никаких внешних сервисов, LibreOffice и CDN; полная автономность по ТЗ §8). Клиент лишь
скачивает готовый файл; право `export` проверяется сервером для каждого документа, событие
пишется в M15 (категория BUSINESS), отказ — SECURITY.

| Документ | Модуль | Форматы |
|---|---|---|
| Портфель проектов (реестр + диаграммы) | M01 | DOCX, XLSX, PDF, CSV, HTML |
| Паспорт проекта (сведения, задачи, риски, документы, расчёты, подписи) | M01 | DOCX, XLSX, PDF |
| Реестр задач (фильтры: проект, статус, исполнитель; просрочки) | M02 | DOCX, XLSX, PDF, CSV |
| Календарный график работ (таблица + длительности) | M04 | DOCX, XLSX, PDF |
| Загрузка ресурсов (план/факт по сотрудникам) | M05 | DOCX, XLSX, PDF |
| Табель трудозатрат (период, сотрудник, итоги, подписи) | M06 | DOCX, XLSX, PDF, CSV |
| Реестр рисков (баллы, мероприятия, профиль рисков) | M08 | DOCX, XLSX, PDF, CSV |
| Протокол инженерного расчёта (исходные данные, результаты, формулы, история, подписи) | M10 | DOCX, XLSX, PDF |
| Отчёт из сохранённого снимка (структура сохраняется) | M13 | DOCX, XLSX, PDF, HTML |
| Протокол совещания (8 разделов ТЗ §2.8) | M16 | DOCX, XLSX, PDF, HTML |
| Отчёт по поручениям (7 видов §2.11.2: реестр, просроченные, исполнители, совещания, проекты, период, неисполненные решения) | M16 / M13 | DOCX, XLSX, PDF, CSV, HTML |
| Журнал событий | M15 | DOCX, XLSX, PDF, CSV |
| Панель показателей (виджеты пользователя) | M17 / M00 | PDF, XLSX, DOCX |

**Соответствие требованиям к форматам:**

- **DOCX (§25.1):** стили заголовков, автоматическая нумерация списков, таблицы с повторяющейся
  шапкой, колонтитулы, номера страниц полями `PAGE`/`NUMPAGES`, оглавление полем `TOC`,
  блок подписей, корректная кириллица.
- **PDF (§25.2):** встроенные шрифты TrueType (DejaVu, подмножество Used-глифов), кириллица,
  перенос строк, таблицы с границами и повтором шапки на новых страницах, **векторные диаграммы**
  (столбцы, линия, круговая), нумерация «Стр. N из M», метаданные, печать.
- **XLSX (§25.3):** отдельные листы для логически разных наборов, автофильтр, закрепление шапки,
  типы данных (числа/даты), форматы дат и чисел, итоговые формулы `SUM`, указание источника и
  даты формирования, **пустые значения не подменяются нулями**.
- **CSV** — BOM UTF-8 и разделитель `;` (корректное открытие в Excel), **HTML** — автономный
  документ без внешних ссылок, **JSON** — резервная копия и API.

**Протокол совещания → M09.** Кнопка «Протокол в M09 (DOCX+PDF)» (или RPC `meeting.protocol`)
формирует протокол по структуре ТЗ §2.8 (общие сведения, присутствовали, повестка, рассмотрение
вопросов, принятые решения, контроль исполнения, подписи, приложения), регистрирует документ
в M09 и сохраняет **обе формы представления одной версии**: DOCX — редактируемый оригинал,
PDF — финальный документ. Скачивание: `/api/files/{docId}/{v}` (DOCX) и
`/api/files/{docId}/{v}?fmt=pdf` (PDF). Повторное формирование создаёт новую версию.

**API выгрузки:** `GET /api/export?kind=<вид>&id=<объект>&fmt=<формат>` (фильтры — `projectId`,
`status`, `assignee`, `from`, `to`, `userId`), `POST /api/export` — для панели M17 с данными
виджетов и для отчётов по поручениям (`kind=directives`, `params.kind=<вид отчёта>`). `GET /api/formats` — доступные форматы (используется диагностикой и `--selftest`).

## 7б. Центр уведомлений и напоминаний (M12 §8, M16 §2.11.1)

Уведомления формирует и доставляет **сервер** — клиент только отображает доставленное.
Канал доставки — внутренний центр уведомлений (`web`): автономная ЛВС без интернета,
внешней почты и CDN (ТЗ §8). Каждое уведомление хранится с адресатом, типом, модулем,
объектом, датой, каналом, статусом, текстом ошибки и датой прочтения.

**Что доставляется автоматически**

| Событие | Тип уведомления | Получатели |
|---|---|---|
| Создано совещание / добавлен участник | `meeting.invite` | председатель, секретарь, участники (кроме автора операции) |
| Совещание перенесено | `meeting.reminder` | тот же состав; напоминания пересчитываются от новой даты |
| Наступил срок напоминания | `meeting.reminder`, `event.reminder` | адресаты напоминания |
| Протокол утверждён | `protocol.approved` | участники совещания |
| Назначена задача / передана другому | `task.assigned` | исполнитель |
| Назначено поручение по решению совещания | `directive.assigned` | исполнитель поручения |
| Срок задачи истекает (≤ 1 дня) / просрочка задачи | `task.due`, `task.overdue` | исполнитель |
| Приближается срок поручения (порог настраивается) | `directive.due` | настраиваемый круг (§2.11.1) |
| Просрочка поручения | `directive.overdue` | настраиваемый круг (§2.11.1) |
| Поручение без исполнителя / без срока | `directive.noassignee`, `directive.nodue` | настраиваемый круг (§2.11.1) |
| Поручение без обновления состояния (порог настраивается) | `directive.stale` | настраиваемый круг (§2.11.1) |
| Поручение требует проверки результата | `directive.review` | настраиваемый круг (§2.11.1) |
| Трудозатраты отправлены / рассмотрены | `time.approval`, `time.result` | утверждающие / автор записи |
| Документ на согласовании, расчёт выполнен | `doc.approval`, `calc.verify` | роли с правом `approve` по матрице M14 |
| Документ утверждён | `doc.approved` | автор документа |
| Наступил срок пересмотра риска | `risk.review` | владелец риска |

**Напоминания (M12 §8.2).** Для совещания и события календаря задаётся несколько интервалов:
в момент начала, за 1 час, за 1 день, за 3 дня, за 7 дней, за 14 дней. Типовой набор при
создании — за 1 день и за 1 час. Интервалы редактируются в карточке совещания (вкладка
«Информация») и в карточке события календаря при праве редактирования; в форме нового
события — чекбоксами. Перенос события пересчитывает время срабатывания.

**Планировщик.** Фоновый поток сервера отрабатывает каждые 30 с (и при запуске службы
Windows): доставляет наступившие напоминания, выявляет приближающиеся сроки и просрочки,
формирует ежедневные сводки очередей утверждения, удаляет прочитанные уведомления старше
90 дней. Повторная доставка одного и того же события исключается ключом дедупликации
(`notifications.dedupe UNIQUE`), отметка о доставке напоминания хранится в `reminders.sent_at`.
Внеочередной цикл — `notif.tick` (только администратор): в M14 → «Система» карточка
«Планировщик уведомлений и напоминаний» показывает число настроенных, ожидающих и доставленных
напоминаний и кнопку запуска внеочередного цикла.

**Интерфейс.** Колокольчик в шапке показывает число непрочитанных; в попапе — доставленные
уведомления (переход к объекту по клику, автоматическая отметка о прочтении), кнопка
«Прочитать все» и раздел «Требует внимания» — производные подсказки из текущего состояния.
Шестерёнка открывает персональную настройку типов: отключённые типы не доставляются
(настройка хранится на сервере в `settings.notifPrefs`).

**RPC:** `notif.list`, `notif.read` (`{ids:[…]}` или `{all:true}`), `notif.prefs`,
`reminder.set`, `reminder.list`, `reminder.remove`, `notif.tick`.
**Аудит:** `calendar.reminder.created`, `calendar.reminder.sent`, `calendar.reminder.failed`
(сбой цикла), изменение настроек уведомлений — события в M15.
**Схема БД:** версия 2. Прежняя БД обновляется миграцией `MIGRATIONS[2]` при старте сервера
(`CREATE TABLE IF NOT EXISTS notifications / reminders` + индексы), событие TECH в M15.

## 7в. Файловые журналы: установка, запуск, работа (ТЗ §15)

Журналы пишутся **на диске сервера независимо от БД** — причина сбоя видна даже тогда,
когда PostgreSQL недоступен и журнал событий M15 записать невозможно.

| Файл | Что содержит |
|---|---|
| `data/logs/installer.log` | журнал NSIS-установщика: все шаги, команды, коды возврата и их вывод (исходник — `%TEMP%\SUP-IP-Setup.log`) |
| `data/logs/setup.log` | мастер установки/настройки (`--install`, `--install-auto`), самотестирование поставки, ошибки подключения к СУБД с трассировкой |
| `data/logs/supip.log` | работа сервера: запуск и остановка, версия и параметры, миграции, HTTP-запросы, **каждая RPC-операция** (пользователь, результат, длительность), отказы прав, внутренние ошибки с трассировкой, входы и блокировки, циклы планировщика, резервные копии |
| журнал клиента (буфер браузера) | последние 300 событий вкладки: ошибки интерфейса, необработанные отклонения промисов, отказы операций, недоступность сервера — доступен и выгружается, даже когда сервер не отвечает |

**Ротация:** 10 МБ × 5 файлов на журнал (настраивается). **Пароли в журнал не пишутся** —
строка подключения маскируется (`password=***`).

**Просмотр и выгрузка:** M14 → «Система» → карточка **«Файловые журналы»**: кнопки «Журнал
работы», «Журнал настройки», «Журнал установщика», «Журнал клиента»; в окне — последние
400 строк, переключение между файлами, «Обновить» и «Скачать». Ярлыки журналов создаются
в меню «Пуск» → СУП-ИП. API: `GET /api/logs` (список), `GET /api/logs/<имя>?tail=N`
(последние строки) и `GET /api/logs/<имя>` (файл целиком) — только администратор;
имя файла проверяется по шаблону, обход каталога исключён. RPC: `admin.logs`.

**Настройка:** `supip.ini` → секция `[logs]` (`level`, `dir`, `max_mb`, `keep`) либо ключи
`--log-level DEBUG|INFO|WARNING|ERROR` и `--log-dir <каталог>`. Уровень `DEBUG` дополнительно
пишет поллинг состояния (`/api/state`), который в `INFO` не журналируется.

**Что присылать при сбое:** `installer.log` + `setup.log` (проблема установки/запуска) либо
`supip.log` + журнал клиента (проблема в работе). По ним восстанавливается вся
последовательность шагов и точная причина отказа.

## 7г. Маршрут согласования и версии протокола (M16 §2.9)

Протокол совещания проходит настраиваемый маршрут согласования и хранится редакциями.

**Статусы протокола (8, по ТЗ §2.9):** Подготовка → Черновик → Направлен на согласование →
(На доработке) → Согласован → Утверждён → Опубликован → Архивный.
Статус виден в шапке карточки совещания, на вкладке «Протокол» и в реестре совещаний
(режим «Протоколы»); при проведении совещания протокол автоматически переходит в «Черновик».

**Маршрут согласования.** Состав и порядок задаются вручную (кнопка «Маршрут»): секретарь,
председатель, руководитель подразделения и иные назначенные согласующие — до 8 шагов,
повторные назначения одного лица исключаются. Кнопка «Типовой маршрут» строит цепочку
секретарь → председатель → руководитель подразделения; если маршрут не настроен, он
применяется автоматически при направлении. Маршрут можно менять только в статусах
Подготовка / Черновик / На доработке.

**Регистрируемые сведения:** дата направления и автор, согласующее лицо и его роль,
результат каждого шага («Согласовано» / «Замечания»), текст замечаний, дата результата,
дата утверждения, утверждающее лицо, дата публикации, номер версии протокола.

**Правила переходов**

| Операция | Кто | Условие |
|---|---|---|
| `protocol.route` | право `meetings.edit` | статус Подготовка / Черновик / На доработке |
| `protocol.send` | право `meetings.edit` | совещание проведено; статус Подготовка / Черновик / На доработке |
| `protocol.review` | текущий согласующий (или администратор) | статус «Направлен на согласование»; замечания требуют текста |
| `protocol.approve` | право `meetings.approve` | статус «Согласован» (или протокол без маршрута) |
| `protocol.newVersion` | право `meetings.edit` | статус Утверждён / Опубликован / Архивный |
| `protocol.publish` | право `meetings.approve` | статус «Утверждён» |
| `protocol.archive` | право `meetings.approve` | статус Утверждён / Опубликован |

Согласование вне своей очереди отклоняется с кодом 403 и указанием текущего согласующего.
«Замечания» возвращают протокол секретарю (статус «На доработке») с уведомлением;
после доработки протокол направляется повторно, и маршрут проходится заново.
Последнее «Согласовано» переводит протокол в статус «Согласован».

**Версии.** Утверждение сохраняет **отдельную редакцию**: файлы DOCX и PDF регистрируются
в M09 как новая версия документа «Протокол совещания СОВ-…», а в самой редакции хранится
снимок повестки и решений на момент утверждения. Изменение утверждённого протокола возможно
только через «Новую редакцию»: протокол возвращается в «Черновик», история предыдущих
редакций и их файлы сохраняются и остаются доступными для скачивания. Кнопка просмотра
редакции показывает сохранённый снимок содержания.

**Интерфейс.** Карточка совещания → вкладка «Протокол»: блок «Согласование протокола»
(статус, даты, текущий согласующий, кнопки действий), таблица маршрута (№, согласующий,
роль, результат, дата, замечания), «История редакций» с выгрузкой DOCX/PDF каждой редакции,
лента замечаний и отметок маршрута. Печатная форма протокола дополнена разделом
«Согласование и утверждение» (статус, номер версии, даты, согласующие, утверждающее лицо).

**Уведомления:** `protocol.review` (очередь согласования), `protocol.rework` (возврат на
доработку), `protocol.approved` (согласован / утверждён), `protocol.published` (публикация).
**Аудит (M15):** `MEETING_PROTOCOL_ROUTE_SET`, `MEETING_PROTOCOL_SENT_FOR_APPROVAL`,
`MEETING_PROTOCOL_REWORK`, `MEETING_PROTOCOL_AGREED`, `MEETING_PROTOCOL_APPROVED`,
`MEETING_PROTOCOL_VERSION_CREATED`, `MEETING_PROTOCOL_PUBLISHED`, `MEETING_PROTOCOL_ARCHIVED`.
**Схема БД:** версия 3 — в таблицу `meetings` добавлено поле `protocol JSONB`
(миграция `MIGRATIONS[3]` применяется при старте сервера, событие TECH в M15).
Прежний вызов `meeting.approve` сохранён и работает через единый контур §2.9.

## 7д. Поручения из решений совещаний (M16 §2.10)

Каждое решение совещания может быть преобразовано в **поручение — обычную задачу M02**
(единая система задач; отдельная параллельная система поручений не создаётся, техпроект §4.1).

**Поля, заполняемые при создании поручения (все по ТЗ §2.10):** наименование, описание,
проект, постановщик, исполнитель, соисполнители, дата постановки, срок исполнения, приоритет,
критерии завершения, источник поручения, ссылка на совещание, ссылка на протокол,
ссылка на пункт решения (и пункт повестки). Незаполненные поля подставляются автоматически:
проект — по исполнителю, описание и источник — из формулировки решения, срок — из решения,
приоритет — «Высокий», дата постановки — текущая дата сервера.

**Где хранится.** Реквизиты поручения — в задаче M02 (`tasks.directive`): источник, критерии,
соисполнители, дата и автор постановки, ссылки на совещание/решение/пункт повестки/редакцию
протокола и документ M09. Связь «решение ↔ задача» хранится в таблице `meeting_tasks`
(одно решение может порождать несколько задач).

**Правила**

| Правило ТЗ | Реализация |
|---|---|
| Одно решение → несколько задач | `meeting.decision.toTask` добавляет задачу в `decision.taskIds`, связь — в `meeting_tasks` |
| Запрет повторного создания без подтверждения | повторный вызов возвращает **409 `NEED_CONFIRM`** с перечнем уже созданных поручений; в интерфейсе — диалог подтверждения, повтор с `confirm:true` |
| Правка решения не создаёт задачу заново | `meeting.decision.update` меняет формулировку/ответственного/срок/пункт повестки и сохраняет связи |
| Обратная связь | из протокола — переход к задаче; из задачи — блок «Основание поручения» с переходом к совещанию, решению и документу протокола |
| Источник поручения в карточке задачи | поле «Источник поручения» в блоке «Основание поручения» (M02) |

**Интерфейс.** Карточка совещания → «Решения»: у каждого решения кнопки «В поручение» /
«Ещё поручение» (форма со всеми полями §2.10) и правка решения; созданные поручения показаны
чипами со статусом. Вкладка «Поручения» — список с соисполнителями и критериями.
Карточка задачи M02 → блок **«Основание поручения»**: совещание, номер решения и его
формулировка, пункт повестки, редакция протокола и документ, дата постановки и постановщик,
соисполнители, источник, критерии завершения. Печатная форма протокола и DOCX/PDF включают
перечень поручений по каждому решению, соисполнителей и критерии завершения.

**Уведомления:** `directive.assigned` — исполнителю и каждому соисполнителю.
**Аудит (M15):** `MEETING_DIRECTIVE_CREATED` (с источником, исполнителем, соисполнителями и сроком),
`MEETING_DECISION_UPDATED`.
**Схема БД:** версия 4 — `tasks.directive JSONB` и таблица `meeting_tasks` (миграция
`MIGRATIONS[4]`); резервная копия — 16 таблиц, копии прежних версий восстанавливаются.
Удаление задачи снимает связь с решением, само решение сохраняется.

## 7е. Реестр поручений и контроль исполнения (M16 §2.11, §19.5–19.6)

M16 → **«Поручения»** — отдельный реестр поручений, сформированных по итогам совещаний,
и режим **«Просроченные поручения»**. Реестр — представление задач M02 (единый владелец
данных), а не параллельная система задач.

**Состав реестра (все поля ТЗ §2.11):** номер поручения, совещание, номер протокола (редакция),
формулировка решения, исполнитель, соисполнители, срок исполнения, статус, процент выполнения,
дата фактического исполнения, результат, комментарий, документы, подтверждающие выполнение.
Фильтры: совещание, исполнитель (с учётом соисполнителей), проект, статус, «только просроченные»,
период срока, поиск по формулировке; выгрузка реестра — CSV (Excel).

**Статусы поручения и синхронизация с задачей**

| Статус реестра | Условие (статус задачи M02 / приёмка) |
|---|---|
| Не начато | Черновик / Новая / Запланирована / Готова к выполнению |
| В работе | В работе, Возвращена на доработку |
| Ожидает информации | Заблокирована |
| На проверке | На проверке |
| Ожидает подтверждения | Принята / Закрыта, но результат ещё не принят руководителем |
| Выполнено | результат принят руководителем (`directive.accept` → Принято) |
| Просрочено | срок истёк, работа не завершена (вычисляется автоматически) |
| Приостановлено | Приостановлена |
| Отменено | Отменена (снято с контроля) |

**Отдельный контроль результата.** Технически закрытая задача не означает, что решение совещания
исполнено: статус «Выполнено» устанавливается только после приёмки руководителем
(право `meetings.approve`). Приёмка «Принято» фиксирует автора, дату, комментарий и дату
фактического исполнения, закрывает задачу; «На доработку» (комментарий обязателен) возвращает
задачу исполнителю в статус «Возвращена на доработку».

**Продление срока** (`directive.extend`) допускается только на более позднюю дату и требует
основания: каждая запись истории хранит инициатора, дату, прежний и новый срок и основание
(ТЗ §19.6). Завершённые и отменённые поручения не продлеваются.

**Подтверждающие документы** (`directive.attach` / `directive.detach`) — ссылки на документы M09
(код, наименование, версия); сами документы остаются в M09, копирования данных нет.

**Карточка поручения.** Карточка задачи M02 → вкладка **«Поручение»**: статус реестра и статус
задачи, совещание и решение, номер протокола, срок и просрочка, дата факта, процент выполнения,
редактируемые результат / дата факта / комментарий / критерии, блок приёмки, документы и история
продления. Кнопки: «Продлить срок», «Приложить документ», «Приёмка результата».

**RPC:** `directive.list` (фильтры и сводка по статусам), `directive.update`, `directive.extend`,
`directive.accept`, `directive.attach`, `directive.detach`.
**Уведомления:** `directive.extended`, `directive.accepted`, `directive.rework` — состав
получателей определяется настройкой контроля поручений (§7ж): исполнитель, соисполнители,
председатель, секретарь, руководитель подразделения, контролирующее лицо.
**Аудит (M15):** `MEETING_DIRECTIVE_UPDATED`, `MEETING_DIRECTIVE_EXTENDED`,
`MEETING_DIRECTIVE_ACCEPTED`, `MEETING_DIRECTIVE_REWORK`, `MEETING_DIRECTIVE_DOC_ATTACHED`.

## 7ж. Контроль сроков и отчётность по поручениям (M16 §2.11.1–2.11.2)

M16 → **«Контроль сроков»** и **«Отчётность»**. Контроль выполняется сервером: планировщиком
(каждые 30 с) и внеочередным проходом по кнопке «Выполнить контроль и разослать».

**Автоматически выявляемые отклонения (шесть категорий §2.11.1)**

| Категория | Условие выявления | Тип уведомления |
|---|---|---|
| Приближается срок исполнения | до срока ≤ `dueSoonDays` (по умолчанию 3 дня) | `directive.due` |
| Просрочено | срок прошёл, работа не завершена | `directive.overdue` |
| Без исполнителя | исполнитель не назначен или заблокирован | `directive.noassignee` |
| Без установленного срока | срок исполнения не задан | `directive.nodue` |
| Без обновления состояния | статус/процент/результат/срок не менялись > `staleDays` (по умолчанию 7 дней) | `directive.stale` |
| Требует проверки результата | «На проверке» либо задача закрыта, но результат не принят руководителем | `directive.review` |

Принятые («Выполнено») и отменённые поручения контролю не подлежат. Момент последнего
обновления состояния хранится в `tasks.directive.stateAt` и обновляется при смене статуса,
процента, результата, даты факта, срока и при приёмке.

**Настраиваемый состав получателей.** В настройке контроля (M16 → «Контроль сроков» →
«Настроить контроль», право `admin.edit`) включаются/отключаются: исполнитель, соисполнители,
председатель совещания, секретарь совещания, руководитель подразделения, контролирующее лицо.
Там же задаются пороги `dueSoonDays` (1…30) и `staleDays` (1…90), состав проверок и
контролирующее лицо по умолчанию. Контролирующее лицо можно назначить и в карточке
конкретного поручения. Заблокированные пользователи в рассылку не попадают; хотя бы один
получатель и хотя бы одна проверка должны остаться включёнными. Настройка хранится
в `settings.dirControl` и входит в резервную копию.

**Защита от повторов.** Уведомление по каждой категории доставляется адресату не чаще одного
раза в сутки на поручение (ключ дедупликации `тип:адресат:поручение:дата`). Просрочка
дополнительно фиксируется событием `MEETING_TASK_OVERDUE` (ТЗ §2.13) — также не чаще раза в сутки.

**Отчётность: семь видов отчётов (§2.11.2)**

| Вид отчёта | Содержание |
|---|---|
| Реестр всех поручений | все поля §2.11 + сводка по состояниям и круговая диаграмма |
| Перечень просроченных поручений | сортировка по убыванию просрочки, максимальная/средняя просрочка, продления |
| Отчёт по исполнителям | группировка по исполнителю, состояния, исполнительская дисциплина, средняя просрочка |
| Отчёт по совещаниям | число решений и поручений, исполнение, решения без поручений |
| Отчёт по проектам | поручения проекта, исполнение, трудозатраты по поручениям (M06) |
| Отчёт по исполнению за период | поставлено / исполнено / принято / просрочено, продления срока, дисциплина исполнения |
| Отчёт по неисполненным решениям | решения без созданных поручений и поручения, не принятые руководителем |

Отборы: совещание, проект, исполнитель, период (для отчёта за период — обязателен, по умолчанию
последние 30 дней). Отчёт формирует сервер; выгрузка — DOCX/XLSX/PDF/CSV/HTML через единый
контур экспорта (`kind=directives`), кнопка «Снимок в M13» сохраняет отчёт в реестре отчётов
(право `reports.create`) с фиксацией данных на момент формирования.

**RPC:** `directive.control` (категории, счётчики, получатели, действующая настройка),
`directive.controlConfig` (чтение — `meetings.view`, изменение — `admin.edit`),
`directive.controlNotify` (внеочередной проход, `meetings.approve`), `directive.report`
(`{kind, meetingId, projectId, assignee, from, to, save}`), `directive.reportKinds`.
**Аудит (M15):** `MEETING_TASK_OVERDUE`, `MEETING_TASK_CREATED`, `MEETING_TASK_COMPLETED`,
`MEETING_DIRECTIVE_CONTROL_CONFIG`, `MEETING_DIRECTIVE_CONTROL_RUN`, `MEETING_DIRECTIVE_REPORT`.

## 7з. Установка и запуск: диагностика отказов (исправления 1.9.0 и 1.11.0)

Раздел собран по журналам реальной установки (`installer.log`, `setup.log`, `supip.log`).
Для каждого признака указана причина и то, что изменено в программе.

| Признак в журнале | Причина | Исправлено в 1.9.0 |
|---|---|---|
| «Режим PostgreSQL: auto» при включённом офлайн-пакете → загрузка 357 МБ → «УСТАНОВКА ПРЕРВАНА» | радиокнопки страницы PostgreSQL проверялись по одной (`NSD_Check`), выбор «из файла» не снимал выбор «скачать»; режим определялся по остаточному состоянию | переключение одной группой (`PgPickExist/PgPickFile/PgPickAuto`); при включённом пакете режим принудительно меняется на офлайн — и на странице, и в секции установки |
| «Загружено:  МБ» → «файл повреждён или неполон» при фактически скачанном файле | размер файла запрашивался макросом `${GetSize}` (Locate), который вернул пустую строку → сравнение «меньше 100 МБ» срабатывало ложно | размер берётся по факту (`FileOpen`/`FileSeek … END`/пересчёт байтов), в журнале и МБ, и байты; при неполной загрузке автоматически используется офлайн-пакет |
| Нечитаемый `installer.log`: часть строк кириллицей, часть «кракозябрами», вывод команд обрезан | NSIS писал журнал в ANSI (cp1251), а вывод дочерних процессов приходил в UTF-8/OEM; `nsExec` обрезает длинный вывод | журнал — UTF-16LE с BOM; вывод команды пишется в файл и дописывается в журнал с распознаванием UTF-8, при отказе — CP866; длина вывода не ограничена |
| «Порт 8443: свободен» одновременно с «сервер слушает 0.0.0.0:8443» | на Windows `SO_REUSEADDR` разрешает связывание уже занятого порта — проба всегда сообщала «свободен» | проба в исключительном режиме (`SO_EXCLUSIVEADDRUSE`) **и** проверка фактического ответа `/api/health`; однозначные формулировки состояния порта |
| «Служба установлена и запущена», но сервер не отвечает | служба Windows поднимается асинхронно, мастер не проверял факт запуска | мастер ожидает ответ `/api/health` до 40 с и пишет результат в отчёт и `setup.log`; при отсутствии ответа — предупреждение с указанием, что смотреть |
| «Планировщик уведомлений: доставлено 10» каждые 30 с при отсутствии новых уведомлений | счётчик увеличивался безусловно даже когда доставка подавлена защитой от повторов | считаются только реально доставленные (`if notify(...)`); повторный цикл показывает «Доставлено уведомлений: 0» |
| `--backup-now` до установки PostgreSQL: CRITICAL + traceback, код 2; установщик считал это отказом | отсутствие БД при первой установке — штатная ситуация | предупреждение (WARNING) с понятным текстом и **код 3**; установщик трактует его как «копия пропущена» и продолжает установку |
| `--service stop` перед первым запуском: ошибка `(1060, 'GetServiceKeyName')`, код 1 | служба ещё не установлена | для `stop`/`restart`/`remove` отсутствие службы (winerror 1060) — штатный исход: сообщение «Служба не установлена — … не требуется», код 0 |
| **Обновление поверх установленной версии:** `Служба: (1073, 'CreateService', 'Указанная служба уже существует.')` → «Служба Windows: не установлена» → «Проверка порта 8443: свободен — сервер НЕ запущен», при этом «УСТАНОВКА ЗАВЕРШЕНА» | мастер всегда вызывал `CreateService`; при обновлении служба уже есть, отказ 1073 считался ошибкой, служба не перенастраивалась и не запускалась | **1.11.0:** при 1073 служба **перенастраивается** (`sc config … binPath= … start= auto`, описание) на новый EXE, перезапускается, состояние проверяется по факту (`QueryServiceStatus`, ожидание до 20 с); в отчёте — «обновлена (уже была установлена), состояние: работает» |
| `--health` печатает «Сервер: НЕ ОТВЕЧАЕТ … WinError 10061», но возвращает **код 0** — установщик рапортует успех | код возврата зависел только от БД и файлового хранилища | **1.11.0:** код **4** = сервер не отвечает; в выводе — состояние службы и подсказка запуска; установщик при коде 4 повторно запускает службу, проверяет ещё раз и показывает инструкцию, а итог пишет как «УСТАНОВКА ЗАВЕРШЕНА С ПРЕДУПРЕЖДЕНИЕМ» |
| Мастер настройки завершался кодом 0, даже если служба не поднялась | код возврата не учитывал результат проверки запуска | **1.11.0:** `--install-auto` возвращает 4, если служба запрошена, но сервер не отвечает; в отчёте — строка «ВНИМАНИЕ…» и порядок действий |
| `installer.log` нечитаем: начало кириллицей (cp1251), середина — «разряжённый» текст | журнал `%TEMP%\SUP-IP-Setup.log` **дописывался**: UTF-16LE новой версии попадал в ANSI-файл прежней версии | **1.11.0:** каждый запуск создаёт **новый** журнал UTF-16LE с BOM, прежний сохраняется как `SUP-IP-Setup.prev.log` (и `SUP-IP-Uninstall.prev.log`) — смешение кодировок исключено |
| В M14 «Журнал установки» показывал «кракозябры», выгрузка открывалась нечитаемой | сервер читал любой журнал как UTF-8, а журнал установщика — UTF-16LE | **1.11.0:** распознавание UTF-16LE/BE с BOM, UTF-8 (в т.ч. с BOM), cp1251 и cp866; хвост большого UTF-16-журнала не разрывает кодовые единицы; выгрузка по HTTP отдаёт правильную `charset` |
| PostgreSQL переустанавливался поверх работающей СУБД (3 минуты, «Please ensure the pgAdmin server is shutdown…») | режим «из файла» выполнял установку безусловно | **1.11.0:** если обнаружена служба `postgresql-x64-16` и сервер уже принимает соединения — установка СУБД пропускается с записью в журнал |
| `--service start` при работающей службе / `stop` при остановленной — ошибка | коды 1056 и 1062 не распознавались | **1.11.0:** «Служба уже запущена» / «Служба не запущена — остановка не требуется», код 0; добавлена команда `--service status` |

**Коды возврата `SUP-IP.exe` (для сценариев установки):**

| Код | Значение |
|---|---|
| 0 | успешно (в т.ч. «служба не установлена — действие не требуется») |
| 1 | отказ операции (см. вывод и `data/logs/supip.log`) |
| 2 | PostgreSQL недоступен при обычном запуске — требуется мастер установки |
| 3 | резервная копия пропущена: БД недоступна (первая установка либо СУБД не запущена) |
| 4 | сервер не отвечает: служба не установлена/не запущена (`--health`, `--install-auto`, `--service status`) — программа установлена, но требует запуска службы |

**Проверка запуска после установки:** `SUP-IP.exe --health` теперь сообщает не только
состояние БД и файлового хранилища, но и факт ответа сервера:

```
Сервер: ОТВЕЧАЕТ https://127.0.0.1:8443/api/health (версия 1.11.0, БД PostgreSQL)
Проверка порта 8443: занят службой СУП-ИП (ожидаемо)
```

Если сервер не поднялся, вывод прямо указывает это («свободен — сервер НЕ запущен») и
отличает занятость порта посторонним процессом от штатной занятости своей службой.

Команды установщик выполняет через пакетный файл в **системной кодовой странице**: смена
кодовой страницы внутри bat искажала бы кириллические пути (`C:\Users\Иван\AppData\Local\Temp`,
каталог с офлайн-установщиком на флешке). Вывод Python принудительно переводится в UTF-8
переменной `PYTHONIOENCODING`, вывод системных утилит распознаётся как CP866.

**Чем открывать журнал установщика:** «Блокнот», Notepad++, VS Code — кодировка UTF-16LE
определяется автоматически. Журнал пишется в `%TEMP%\SUP-IP-Setup.log` с первого шага и
копируется в `data\logs\installer.log`; журнал деинсталляции — `%TEMP%\SUP-IP-Uninstall.log`.
Предыдущий запуск сохраняется рядом (`*.prev.log`) — можно сравнить две установки.
В M14 «Файловые журналы» журналы установщика и прежних версий читаются корректно (UTF-16LE,
UTF-8, cp1251, cp866).

**Обновление версии (1.11.0).** Установщик останавливает службу, делает резервную копию БД,
копирует файлы, при необходимости готовит PostgreSQL (работающая СУБД той же версии не
переустанавливается), затем **перенастраивает существующую службу на новый EXE** и запускает её.
Данные и настройки сохраняются; схема БД дополняется миграцией. Проверка после обновления —
`SUP-IP.exe --health` (код 0) или ярлык «Проверка работоспособности» в меню «Пуск».
Ярлыки «Запуск сервера (служба)», «Остановка сервера (служба)», «Состояние службы» позволяют
управлять сервером без командной строки (запуск службы — от имени администратора).

**Что присылать при сбое установки:** `installer.log` + `setup.log` + `data\install-report.txt`.
По ним восстанавливается вся последовательность: выбранный источник СУБД, фактические команды,
их коды возврата и полный вывод, результат ожидания готовности PostgreSQL и запуска службы.

## 7и. Планирование совещаний (M16 §2.5)

M16 → **«Совещания»**: реестр, карточка совещания → вкладка **«Планирование»**, календарь M12.
Планирование выполняется сервером; клиент только отображает состояние.

**Регистрируемые сведения (§2.5).** Дата и время, тип, председатель, секретарь, состав участников,
**связанные проекты** (до 20), **предварительные материалы** (до 20), правило повторения,
статус совещания и **история планирования** (переносы, отмены, возобновления, изменения расписания,
пропуски дат) с датой, автором и основанием.

**Статусы совещания:** Запланировано → Проведено → Протокол утверждён, отдельно — **Отменено**.
Отменённое совещание нельзя провести, перенести, отредактировать или дополнить материалами;
доступно только «Возобновить». Проведённое совещание нельзя отменить или перенести.

**Правило повторения.** `freq` = без повторения / ежедневно / еженедельно / ежемесячно,
`interval` 1…30 (каждые N дней/недель/месяцев), `weekdays` (Пн…Вс) для еженедельного,
`monthDay` 1…31 для ежемесячного, `until` — дата окончания серии, `count` 1…104 — всего
совещаний серии. Для ежемесячного повторения дата «прижимается» к концу короткого месяца
(31.01 → 28.02 → 31.03 → 30.04). Неизвестная периодичность и некорректное время (ЧЧ:ММ
с реальными часами 00–23 и минутами 00–59) отклоняются сервером.

**Серия — отдельные карточки.** Каждое совещание серии создаётся самостоятельной карточкой
со своим кодом `СОВ-<год>-NNN`, повесткой, решениями и **отдельным протоколом** (§2.5).
Головная карточка (`master`) хранит правило; расписание меняется только в ней, при желании —
с применением времени и состава к будущим совещаниям серии. Автоматическая генерация
идемпотентна: планировщик и создание совещания пополняют серию на **30 дней** вперёд
(не более 60 карточек за операцию), повторный вызов дублей не создаёт; пропущенные даты
(`skipped`) больше не создаются.

**Предварительные материалы.** Документ M09 (с переходом к карточке и скачиванием) либо
ссылка на файл ЛВС/ресурс (`\\server\share\...`, `https://…`). Повторы одного документа
или ссылки не добавляются, схемы `javascript:`, `data:`, `vbscript:` запрещены,
наименование и примечание обязательны для ссылки.

**Правила операций**

| Операция | Кто | Условие |
|---|---|---|
| `meeting.create` | право `meetings.create` | дата/время корректны, проекты существуют, правило повторения допустимо |
| `meeting.projects.set` | право `meetings.edit` | совещание не отменено, до 20 проектов |
| `meeting.materials.add` / `.remove` | право `meetings.edit` | совещание не отменено, до 20 материалов, без дублей и опасных схем |
| `meeting.reschedule` | право `meetings.edit` | статус «Запланировано», дата/время изменились, основание ≥ 3 символов |
| `meeting.cancel` | право `meetings.edit` | статус «Запланировано», основание ≥ 3 символов |
| `meeting.restore` | право `meetings.edit` | статус «Отменено»; дата и время возвращаются в расписание |
| `meeting.series.update` | право `meetings.edit` | головная карточка серии |
| `meeting.series.generate` | право `meetings.edit` | головная карточка; без `count` — горизонт 30 дней, с `count` — N новых дат |
| `meeting.series.skip` | право `meetings.edit` | головная карточка; дата и основание ≥ 3 символов |
| `meeting.series.list` | право `meetings.view` | состав серии с номерами, статусами и признаком головной карточки |

Перенос, отмена и возобновление **пересчитывают напоминания** (M12 §8.2: по умолчанию за сутки
и за час) и оповещают председателя, секретаря и участников; отмена напоминания снимает.
Основание сохраняется в истории планирования и в печатной форме протокола.

**Интерфейс.** Вкладка «Планирование»: дата и время, правило повторения человеческим текстом,
счётчики проектов/материалов/записей истории; кнопки «Перенести», «Отменить совещание»,
«Возобновить», «Расписание»; карточки «Связанные проекты», «Предварительные материалы»,
«Регулярное совещание» (создать ближайшие даты, пропустить дату, состав серии) и «История
планирования». В форме создания — выбор проектов и правило повторения. В реестре — режимы
**«Регулярные»** и **«Отменённые»**, фильтры по статусу и по связанному проекту, сводка
планирования. Отменённые совещания исключены из режима «Предстоящие», из виджета ближайших
совещаний дашборда и помечаются в календаре M12.

**Протокол.** Печатная форма и файлы DOCX/PDF дополнены разделами «Связанные проекты»,
«Предварительные материалы», «Повторение» и «Планирование: переносы, отмены, изменения».

**Уведомления:** `meeting.invite`, `meeting.moved` (перенос и возобновление),
`meeting.cancelled`, `meeting.materials` (новые материалы).
**Аудит (M15):** `MEETING_CREATED`, `MEETING_PROJECTS`, `MEETING_MATERIAL_ADDED`,
`MEETING_MATERIAL_REMOVED`, `MEETING_RESCHEDULED`, `MEETING_CANCELLED`, `MEETING_RESTORED`,
`MEETING_SERIES_UPDATED`, `MEETING_SERIES_OFF`, `MEETING_SERIES_GENERATED`,
`MEETING_SERIES_OCCURRENCE`, `MEETING_SERIES_SKIP`, `MEETING_SERIES_AUTO`.
**Схема БД:** версия 5 — в таблицу `meetings` добавлены поля `materials JSONB`, `projects JSONB`,
`recurrence JSONB`, `plan_log JSONB`, `series_id TEXT` (миграция `MIGRATIONS[5]` применяется
при старте сервера, событие TECH в M15).

## 9. Соответствие ТЗ и принятые отклонения

- **Стек backend:** ТЗ §12 допускает «иной согласованный» стек — использован Python 3 + psycopg2
  вместо предложенного варианта; СУБД — PostgreSQL, как требует §4.1 (SQLite запрещена).
- **EXE:** собирается один автономный файл сервера (PyInstaller). PostgreSQL ставится отдельным
 официальным установщиком — объединять СУБД в один инсталлятор не требуется и не рекомендуется.
- **Инженерные расчёты (M10):** 6 методик с версионированием и проверкой диапазонов
  (бюджет радиолинии, зона покрытия, надёжность, пропускная способность, трудоёмкость ОКР,
  стоимость); формулы приведены в протоколе каждого расчёта.
- **Отчёты (M13):** HTML-снимки с печатью/PDF средствами браузера и выгрузкой HTML; табличные
  выгрузки — CSV (Excel), как предусмотрено ТЗ. Отчёты по поручениям (§2.11.2) дополнительно
  формируются сервером в DOCX/XLSX/PDF/CSV/HTML и сохраняются снимком в реестре M13.
- **Клиентский рендер аналитики:** вычисляется из серверного состояния (единый владелец данных
  не нарушается); сами данные и все мутации — только на сервере.
- **Планирование совещаний (§2.5):** реализовано полностью — связанные проекты, предварительные
  материалы, правило повторения с отдельными карточками серии, перенос/отмена/возобновление
  с основанием и историей, пропуск дат, пересчёт напоминаний и оповещение участников.
  Ближайшие даты серии создаются на 30 дней вперёд (горизонт планировщика), а не «на год»:
  это защищает БД от неограниченного роста и не меняет правило повторения.
- Демо-набор (8 пользователей, 6 проектов, 28 задач, риски, документы, расчёты, совещания)
  создаётся автоматически и служит приёмочными сценариями ТЗ.

# СУП-ИП — система управления проектами инженерного подразделения

**Версия 1.5.0 · клиент-серверная реализация по ТТ-2 (редакция ТЗ 3.0)**

Автономная многопользовательская система для локальной сети: сервер на Python 3 + **PostgreSQL**,
веб-клиенты в браузере без установки. Все 18 модулей M00–M17, серверная проверка прав на каждую
операцию, централизованный аудит, версионирование документов с файловым хранилищем, инженерные
расчёты, резервное копирование и восстановление, HTTPS, серверный центр уведомлений
и напоминаний с планировщиком.

| Способ | Когда выбирать |
|---|---|

## 1. Архитектура (ТЗ §2, трёхуровневая)

| Уровень | Реализация |
|---|---|
| **1. Единое ядро** | `server.py`: PostgreSQL (пул соединений), REST/JSON API, сессии, матрица прав (проверка на сервере при каждой операции), журнал событий (AUDIT / BUSINESS / TECH / SECURITY / INTEGRATION), файловое хранилище `data/files`, резервирование, планировщик уведомлений и напоминаний |
| **2. Функциональные модули** | M00–M17: портфель, задачи, канбан, Гант, ресурсы, трудозатраты, контроль отклонений, риски, документы, расчёты, аналитика, календарь, отчёты, администрирование, журнал, совещания, конструктор дашбордов |
| **3. Веб-интерфейс** | `static/index.html` — SPA без внешних зависимостей и CDN (полная автономность, ТЗ §8). Клиент — представление данных; все мутации выполняются сервером |

**Принцип владения данными:** единственный владелец — серверная БД PostgreSQL. Клиент получает
снимок состояния (`/api/state`), отправляет операции (`/api/rpc`), сервер проверяет права,
валидирует данные, применяет изменение и пишет аудит **в одной транзакции**, затем возвращает
новое состояние. Другие клиенты получают изменения поллингом (~12 с). Производная аналитика
(прогресс, здоровье проектов, отклонения, графики, HTML-отчёты) вычисляется клиентом из единого
состояния; снимок отчёта сохраняется на сервере (M13).

## 2. Требования

- **Сервер:** Windows 10/11 x64 (или Linux), Python 3.10+, **PostgreSQL 14+** (рекомендуется 15/16).
- **Клиенты:** любой современный браузер в ЛВС (Chrome, Edge, Firefox). Установка не требуется.
- **Сеть:** изолированная ЛВС, интернет не нужен (ТЗ §8). До **10 одновременных пользователей** (ТЗ §2).
- SQLite **не используется**: ТЗ §4.1 прямо запрещает её как равнозначную замену PostgreSQL
  в многопользовательском режиме.

## 3. Установка одним EXE (рекомендуется, ТЗ §7)

Готовые файлы собираются автоматически в GitHub Actions — сценарий сборки
[`tools/github/build.yml`](tools/github/build.yml): сначала интеграционные испытания API на
PostgreSQL, затем сборка `SUP-IP.exe` (PyInstaller) и установщика (NSIS). Результат —
**Releases** (по тегу `vX.Y.Z`) и артефакт `SUP-IP-windows-x64` на вкладке Actions.

Автосборка включена: сценарий лежит в `.github/workflows/build.yml` и запускается при каждом
пуше в `main` и при публикации тега версии. Установщик собирается NSIS на Linux-раннере
(`makensis` формирует Windows-инсталлятор и вне Windows) — это исключает зависимость от
Chocolatey и внешних репозиториев на раннере. Сборка `SUP-IP.exe` и его самотестирование
выполняются на `windows-latest`.

- **`SUP-IP-Setup-x.y.z.exe`** — единый установщик: проверка Windows 10/11 x64 и диска → выбор
  каталога → **страница PostgreSQL** (автозагрузка / офлайн-файл / существующий сервер) →
  параметры (пароль PostgreSQL, порт, пароль администратора, HTTPS) → распаковка →
  подготовка СУБД и ожидание её готовности → схема и демо-данные → самоподписанный сертификат
  HTTPS → **служба Windows с автозапуском и автоперезапуском** → правило брандмауэра → проверка
  работоспособности → отчёт `data\install-report.txt` и журнал `data\logs\installer.log`.
- **`SUP-IP.exe`** — самодостаточный сервер (Python и веб-клиент внутри).Режимы:
  - `SUP-IP.exe --install` — интерактивный мастер установки и настройки;
  - `SUP-IP.exe --install-auto params.ini` — автоматическая настройка (используется установщиком);
  - `SUP-IP.exe --service install|start|stop|restart|remove` — служба Windows;
  - `SUP-IP.exe --health` — диагностика (БД, файловое хранилище, порт);
  - `SUP-IP.exe --backup-now` — резервная копия в `data\backups`;
  - `SUP-IP.exe --migrate` — миграции БД при обновлении;
  - `SUP-IP.exe --version` — версия сборки;
  - `SUP-IP.exe --selftest` — проверка целостности поставки без БД (клиент, зависимости, шрифты, каталог данных);
  - `--log-level LEVEL`, `--log-dir DIR` — уровень и каталог файловых журналов (см. §7в).

Консольные режимы (`--install`, `--health`, `--selftest`, `--version`) принудительно переводят
консоль Windows в UTF-8: без этого штатная кодовая страница cp1252 не кодирует кириллицу и
мастер установки завершался бы ошибкой `UnicodeEncodeError`.

**Обновление** (§7.6): новый Setup поверх установленного — автоматически: резервная копия →
остановка службы → замена файлов → миграции БД → запуск → проверка. Откат — восстановлением
копии из `data\backups` (M14 → Восстановить). **Деинсталляция** (§7.7): данные сохраняются по
умолчанию; удаление данных — только явным подтверждением.

**Полностью офлайн-пакет**: `SUP-IP-Setup-full-x.y.z.exe` собирается автосборкой при каждом
теге версии — PostgreSQL 16 включён внутрь и ставится тихо без интернета. Для собственной
сборки положите `postgresql-16.x-windows-x64.exe` как `sup-ip/installer/postgresql-setup.exe`
перед `makensis` (или запустите workflow с `bundle_postgres=true`).

Конфигурация после установки — `supip.ini` рядом с EXE (порт, DSN, сертификат); параметры
командной строки имеют приоритет.

### Сборка установщика на своём Windows-ПК

```bat
sup-ip\installer\build_installer.bat
```
(нужны Python 3.10+ и NSIS; результат — `dist\SUP-IP.exe` и `dist\SUP-IP-Setup-x.y.z.exe`).
Скрипт установщика проверяется компиляцией `makensis installer/setup.nsi` (в т.ч. на Linux),
поэтому ошибки сценария установки выявляются до выпуска сборки.

## 3а. Ручная установка (альтернатива)

1. **PostgreSQL.** Установите PostgreSQL 15/16 с официального установщика (offline). Запомните
   пароль суперпользователя `postgres`. Служба запускается автоматически.
2. **БД и роль.** В `psql` (меню «Пуск → SQL Shell») выполните **по отдельности**:
   ```sql
   CREATE USER supip PASSWORD 'supip';
   CREATE DATABASE supip OWNER supip;
   ```
   (или через pgAdmin). При других имени/пароле — передайте `--dsn` серверу, см. ниже.
3. **Python.** Установите Python 3.10+ (галочка «Add to PATH»), затем:
   ```bat
   python -m pip install psycopg2-binary
   ```
   Для полностью офлайн-установки заранее скачайте wheel: `pip download psycopg2-binary -d wheels`,
   перенесите папку и ставьте `pip install --no-index --find-links wheels psycopg2-binary`.
4. **Запуск.** Дважды щёлкните `run.bat` (или `python server.py --port 8000`).
   При первом запуске сервер создаёт схему и эталонный демо-набор (идемпотентно).
5. **Клиенты.** Откройте `http://<IP-сервера>:8000` в браузере. Брандмауэр Windows: разрешите
   входящий TCP-порт 8000 для профиля «Частная сеть».

### Демо-доступы

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | demo | Администратор |
| `morozov` | demo | Руководитель подразделения |
| `volkova`, `lebedev` | demo | Руководители проектов |
| `novikov`, `kozlova`, `orlov` | demo | Исполнители |
| `zaytseva` | demo | Наблюдатель |

Пароль меняется в профиле (кнопка «Сменить пароль»); администратор может сбросить пароль в M14.
3 неудачные попытки входа блокируют учётку на 60 с; неактивная сессия завершается через
`sessionMin` (M14, по умолчанию 60 мин). Все входы/отказы — категория SECURITY в M15.

### Параметры командной строки

```
python server.py [--host 0.0.0.0] [--port 8000]
                 [--dsn "host=127.0.0.1 port=5432 dbname=supip user=supip password=supip"]
                 [--cert cert.pem --key key.pem]   # HTTPS
                 [--no-seed]                       # не заполнять демо-данные
```
Переменные окружения: `SUPIP_PORT`, `SUPIP_DSN`.

### HTTPS (ТЗ §7)

Сгенерируйте самоподписанный сертификат для имени сервера (openssl есть в комплекте Git/PostgreSQL):
```bat
openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 825 -subj "/CN=supip-server"
python server.py --cert cert.pem --key key.pem
```
Клиенты открывают `https://<IP>:8000` (для самоподписанного сертификата добавьте исключение
или распространите сертификат в доверенные корневые средствами Windows). Cookie сессии
получает флаг `Secure`.

### Автозапуск как службы Windows

Рекомендуется [NSSM](https://nssm.cc) (offline-утилита):
```bat
nssm install SUP-IP "C:\sup-ip\SUP-IP.exe" "--port 8000"
nssm set SUP-IP AppDirectory C:\sup-ip
nssm start SUP-IP
```

## 4. Автономный EXE (Windows x64)

На машине с Python выполните `build_exe.bat` (ставит PyInstaller и собирает один файл):
```bat
python -m pip install pyinstaller psycopg2-binary
pyinstaller --onefile --name SUP-IP --add-data "static;static" server.py
```
Результат `dist\SUP-IP.exe` (~15–20 МБ) содержит сервер и веб-клиент; переносится на целевой ПК
без Python. **PostgreSQL устанавливается отдельно** (требование ТЗ §4.1) — EXE подключается к нему
по `--dsn`. Каталог `data/` создаётся рядом с EXE.

## 6. Резервное копирование и восстановление (M14)

- **Копия:** M14 → Система → «Резервная копия (JSON)» (или `GET /api/backup` под администратором):
  консистентный JSON-дамп всех 15 таблиц, включая пользователей, журнал, уведомления
  и напоминания. Событие TECH в M15.
- **Восстановление:** «Восстановить» → выбрать JSON-копию: данные полностью заменяются в одной
  транзакции, все клиенты получают новое состояние; событие SECURITY в M15.
- **Совместимость:** копии прежних версий (13 таблиц, до v1.4.0) восстанавливаются — отсутствующие
  таблицы уведомлений и напоминаний считаются пустыми.
- **Файлы документов** хранятся в `data/files` — включайте этот каталог в файловые бэкапы.
- Для регулярных копий используйте планировщик Windows + `pg_dump`:
  ```bat
  "C:\Program Files\PostgreSQL\16\bin\pg_dump.exe" -U supip -h 127.0.0.1 -Fc supip > backup_%date%.dump
  ```
- «Сброс демо-данных» пересоздаёт эталонный набор (необратимо, подтверждение + аудит).

## 7. Безопасность (ТЗ §7)

- Пароли: PBKDF2-SHA256, 150 000 итераций, индивидуальная соль; в БД только соль+хеш.
- Сессии: случайный токен 192 бит, cookie `HttpOnly; SameSite=Lax` (+`Secure` при HTTPS),
  idle-таймаут, лимит 10 одновременных пользователей, принудительное завершение при блокировке.
- **Каждая** операция проходит серверную проверку прав (роль × модуль × действие + объектный
  уровень: РП — только свои проекты, исполнитель — только свои задачи/часы). Отказ → HTTP 403
  + событие SECURITY. Матрица прав настраивается в M14 и применяется немедленно.
- SQL — только параметризованные запросы; загрузка файлов — с проверкой прав и лимита 25 МБ.
- Клиентские события журналируются лишь в категориях TECH/INTEGRATION/AUDIT; BUSINESS и
  SECURITY пишет только сервер (подделка записей журнала клиентом невозможна).

## 7а. Документы: DOCX, XLSX, PDF, CSV, HTML (ТЗ §25)

Все документы формирует **сервер** (`docgen.py`, только стандартная библиотека Python —
никаких внешних сервисов, LibreOffice и CDN; полная автономность по ТЗ §8). Клиент лишь
скачивает готовый файл; право `export` проверяется сервером для каждого документа, событие
пишется в M15 (категория BUSINESS), отказ — SECURITY.

| Документ | Модуль | Форматы |
|---|---|---|
| Портфель проектов (реестр + диаграммы) | M01 | DOCX, XLSX, PDF, CSV, HTML |
| Паспорт проекта (сведения, задачи, риски, документы, расчёты, подписи) | M01 | DOCX, XLSX, PDF |
| Реестр задач (фильтры: проект, статус, исполнитель; просрочки) | M02 | DOCX, XLSX, PDF, CSV |
| Календарный график работ (таблица + длительности) | M04 | DOCX, XLSX, PDF |
| Загрузка ресурсов (план/факт по сотрудникам) | M05 | DOCX, XLSX, PDF |
| Табель трудозатрат (период, сотрудник, итоги, подписи) | M06 | DOCX, XLSX, PDF, CSV |
| Реестр рисков (баллы, мероприятия, профиль рисков) | M08 | DOCX, XLSX, PDF, CSV |
| Протокол инженерного расчёта (исходные данные, результаты, формулы, история, подписи) | M10 | DOCX, XLSX, PDF |
| Отчёт из сохранённого снимка (структура сохраняется) | M13 | DOCX, XLSX, PDF, HTML |
| Протокол совещания (8 разделов ТЗ §2.8) | M16 | DOCX, XLSX, PDF, HTML |
| Журнал событий | M15 | DOCX, XLSX, PDF, CSV |
| Панель показателей (виджеты пользователя) | M17 / M00 | PDF, XLSX, DOCX |

**Соответствие требованиям к форматам:**

- **DOCX (§25.1):** стили заголовков, автоматическая нумерация списков, таблицы с повторяющейся
  шапкой, колонтитулы, номера страниц полями `PAGE`/`NUMPAGES`, оглавление полем `TOC`,
  блок подписей, корректная кириллица.
- **PDF (§25.2):** встроенные шрифты TrueType (DejaVu, подмножество Used-глифов), кириллица,
  перенос строк, таблицы с границами и повтором шапки на новых страницах, **векторные диаграммы**
  (столбцы, линия, круговая), нумерация «Стр. N из M», метаданные, печать.
- **XLSX (§25.3):** отдельные листы для логически разных наборов, автофильтр, закрепление шапки,
  типы данных (числа/даты), форматы дат и чисел, итоговые формулы `SUM`, указание источника и
  даты формирования, **пустые значения не подменяются нулями**.
- **CSV** — BOM UTF-8 и разделитель `;` (корректное открытие в Excel), **HTML** — автономный
  документ без внешних ссылок, **JSON** — резервная копия и API.

**Протокол совещания → M09.** Кнопка «Протокол в M09 (DOCX+PDF)» (или RPC `meeting.protocol`)
формирует протокол по структуре ТЗ §2.8 (общие сведения, присутствовали, повестка, рассмотрение
вопросов, принятые решения, контроль исполнения, подписи, приложения), регистрирует документ
в M09 и сохраняет **обе формы представления одной версии**: DOCX — редактируемый оригинал,
PDF — финальный документ. Скачивание: `/api/files/{docId}/{v}` (DOCX) и
`/api/files/{docId}/{v}?fmt=pdf` (PDF). Повторное формирование создаёт новую версию.

**API выгрузки:** `GET /api/export?kind=<вид>&id=<объект>&fmt=<формат>` (фильтры — `projectId`,
`status`, `assignee`, `from`, `to`, `userId`), `POST /api/export` — для панели M17 с данными
виджетов. `GET /api/formats` — доступные форматы (используется диагностикой и `--selftest`).

## 7б. Центр уведомлений и напоминаний (M12 §8, M16 §2.11.1)

Уведомления формирует и доставляет **сервер** — клиент только отображает доставленное.
Канал доставки — внутренний центр уведомлений (`web`): автономная ЛВС без интернета,
внешней почты и CDN (ТЗ §8). Каждое уведомление хранится с адресатом, типом, модулем,
объектом, датой, каналом, статусом, текстом ошибки и датой прочтения.

**Что доставляется автоматически**

| Событие | Тип уведомления | Получатели |
|---|---|---|
| Создано совещание / добавлен участник | `meeting.invite` | председатель, секретарь, участники (кроме автора операции) |
| Совещание перенесено | `meeting.reminder` | тот же состав; напоминания пересчитываются от новой даты |
| Наступил срок напоминания | `meeting.reminder`, `event.reminder` | адресаты напоминания |
| Протокол утверждён | `protocol.approved` | участники совещания |
| Назначена задача / передана другому | `task.assigned` | исполнитель |
| Назначено поручение по решению совещания | `directive.assigned` | исполнитель поручения |
| Срок задачи/поручения истекает (≤ 1 дня) | `task.due`, `directive.due` | исполнитель |
| Просрочка задачи/поручения | `task.overdue`, `directive.overdue` | исполнитель |
| Поручение без обновления > 7 дней | `directive.stale` | председатель и секретарь совещания |
| Трудозатраты отправлены / рассмотрены | `time.approval`, `time.result` | утверждающие / автор записи |
| Документ на согласовании, расчёт выполнен | `doc.approval`, `calc.verify` | роли с правом `approve` по матрице M14 |
| Документ утверждён | `doc.approved` | автор документа |
| Наступил срок пересмотра риска | `risk.review` | владелец риска |

**Напоминания (M12 §8.2).** Для совещания и события календаря задаётся несколько интервалов:
в момент начала, за 1 час, за 1 день, за 3 дня, за 7 дней, за 14 дней. Типовой набор при
создании — за 1 день и за 1 час. Интервалы редактируются в карточке совещания (вкладка
«Информация») и в карточке события календаря при праве редактирования; в форме нового
события — чекбоксами. Перенос события пересчитывает время срабатывания.

**Планировщик.** Фоновый поток сервера отрабатывает каждые 30 с (и при запуске службы
Windows): доставляет наступившие напоминания, выявляет приближающиеся сроки и просрочки,
формирует ежедневные сводки очередей утверждения, удаляет прочитанные уведомления старше
90 дней. Повторная доставка одного и того же события исключается ключом дедупликации
(`notifications.dedupe UNIQUE`), отметка о доставке напоминания хранится в `reminders.sent_at`.
Внеочередной цикл — `notif.tick` (только администратор): в M14 → «Система» карточка
«Планировщик уведомлений и напоминаний» показывает число настроенных, ожидающих и доставленных
напоминаний и кнопку запуска внеочередного цикла.

**Интерфейс.** Колокольчик в шапке показывает число непрочитанных; в попапе — доставленные
уведомления (переход к объекту по клику, автоматическая отметка о прочтении), кнопка
«Прочитать все» и раздел «Требует внимания» — производные подсказки из текущего состояния.
Шестерёнка открывает персональную настройку типов: отключённые типы не доставляются
(настройка хранится на сервере в `settings.notifPrefs`).

**RPC:** `notif.list`, `notif.read` (`{ids:[…]}` или `{all:true}`), `notif.prefs`,
`reminder.set`, `reminder.list`, `reminder.remove`, `notif.tick`.
**Аудит:** `calendar.reminder.created`, `calendar.reminder.sent`, `calendar.reminder.failed`
(сбой цикла), изменение настроек уведомлений — события в M15.
**Схема БД:** версия 2. Прежняя БД обновляется миграцией `MIGRATIONS[2]` при старте сервера
(`CREATE TABLE IF NOT EXISTS notifications / reminders` + индексы), событие TECH в M15.

## 7в. Файловые журналы: установка, запуск, работа (ТЗ §15)

Журналы пишутся **на диске сервера независимо от БД** — причина сбоя видна даже тогда,
когда PostgreSQL недоступен и журнал событий M15 записать невозможно.

| Файл | Что содержит |
|---|---|
| `data/logs/installer.log` | журнал NSIS-установщика: все шаги, команды, коды возврата и их вывод (исходник — `%TEMP%\SUP-IP-Setup.log`) |
| `data/logs/setup.log` | мастер установки/настройки (`--install`, `--install-auto`), самотестирование поставки, ошибки подключения к СУБД с трассировкой |
| `data/logs/supip.log` | работа сервера: запуск и остановка, версия и параметры, миграции, HTTP-запросы, **каждая RPC-операция** (пользователь, результат, длительность), отказы прав, внутренние ошибки с трассировкой, входы и блокировки, циклы планировщика, резервные копии |
| журнал клиента (буфер браузера) | последние 300 событий вкладки: ошибки интерфейса, необработанные отклонения промисов, отказы операций, недоступность сервера — доступен и выгружается, даже когда сервер не отвечает |

**Ротация:** 10 МБ × 5 файлов на журнал (настраивается). **Пароли в журнал не пишутся** —
строка подключения маскируется (`password=***`).

**Просмотр и выгрузка:** M14 → «Система» → карточка **«Файловые журналы»**: кнопки «Журнал
работы», «Журнал настройки», «Журнал установщика», «Журнал клиента»; в окне — последние
400 строк, переключение между файлами, «Обновить» и «Скачать». Ярлыки журналов создаются
в меню «Пуск» → СУП-ИП. API: `GET /api/logs` (список), `GET /api/logs/<имя>?tail=N`
(последние строки) и `GET /api/logs/<имя>` (файл целиком) — только администратор;
имя файла проверяется по шаблону, обход каталога исключён. RPC: `admin.logs`.

**Настройка:** `supip.ini` → секция `[logs]` (`level`, `dir`, `max_mb`, `keep`) либо ключи
`--log-level DEBUG|INFO|WARNING|ERROR` и `--log-dir <каталог>`. Уровень `DEBUG` дополнительно
пишет поллинг состояния (`/api/state`), который в `INFO` не журналируется.

**Что присылать при сбое:** `installer.log` + `setup.log` (проблема установки/запуска) либо
`supip.log` + журнал клиента (проблема в работе). По ним восстанавливается вся
последовательность шагов и точная причина отказа.

## 7г. Маршрут согласования и версии протокола (M16 §2.9)

Протокол совещания проходит настраиваемый маршрут согласования и хранится редакциями.

**Статусы протокола (8, по ТЗ §2.9):** Подготовка → Черновик → Направлен на согласование →
(На доработке) → Согласован → Утверждён → Опубликован → Архивный.
Статус виден в шапке карточки совещания, на вкладке «Протокол» и в реестре совещаний
(режим «Протоколы»); при проведении совещания протокол автоматически переходит в «Черновик».

**Маршрут согласования.** Состав и порядок задаются вручную (кнопка «Маршрут»): секретарь,
председатель, руководитель подразделения и иные назначенные согласующие — до 8 шагов,
повторные назначения одного лица исключаются. Кнопка «Типовой маршрут» строит цепочку
секретарь → председатель → руководитель подразделения; если маршрут не настроен, он
применяется автоматически при направлении. Маршрут можно менять только в статусах
Подготовка / Черновик / На доработке.

**Регистрируемые сведения:** дата направления и автор, согласующее лицо и его роль,
результат каждого шага («Согласовано» / «Замечания»), текст замечаний, дата результата,
дата утверждения, утверждающее лицо, дата публикации, номер версии протокола.

**Правила переходов**

| Операция | Кто | Условие |
|---|---|---|
| `protocol.route` | право `meetings.edit` | статус Подготовка / Черновик / На доработке |
| `protocol.send` | право `meetings.edit` | совещание проведено; статус Подготовка / Черновик / На доработке |
| `protocol.review` | текущий согласующий (или администратор) | статус «Направлен на согласование»; замечания требуют текста |
| `protocol.approve` | право `meetings.approve` | статус «Согласован» (или протокол без маршрута) |
| `protocol.newVersion` | право `meetings.edit` | статус Утверждён / Опубликован / Архивный |
| `protocol.publish` | право `meetings.approve` | статус «Утверждён» |
| `protocol.archive` | право `meetings.approve` | статус Утверждён / Опубликован |

Согласование вне своей очереди отклоняется с кодом 403 и указанием текущего согласующего.
«Замечания» возвращают протокол секретарю (статус «На доработке») с уведомлением;
после доработки протокол направляется повторно, и маршрут проходится заново.
Последнее «Согласовано» переводит протокол в статус «Согласован».

**Версии.** Утверждение сохраняет **отдельную редакцию**: файлы DOCX и PDF регистрируются
в M09 как новая версия документа «Протокол совещания СОВ-…», а в самой редакции хранится
снимок повестки и решений на момент утверждения. Изменение утверждённого протокола возможно
только через «Новую редакцию»: протокол возвращается в «Черновик», история предыдущих
редакций и их файлы сохраняются и остаются доступными для скачивания. Кнопка просмотра
редакции показывает сохранённый снимок содержания.

**Интерфейс.** Карточка совещания → вкладка «Протокол»: блок «Согласование протокола»
(статус, даты, текущий согласующий, кнопки действий), таблица маршрута (№, согласующий,
роль, результат, дата, замечания), «История редакций» с выгрузкой DOCX/PDF каждой редакции,
лента замечаний и отметок маршрута. Печатная форма протокола дополнена разделом
«Согласование и утверждение» (статус, номер версии, даты, согласующие, утверждающее лицо).

**Уведомления:** `protocol.review` (очередь согласования), `protocol.rework` (возврат на
доработку), `protocol.approved` (согласован / утверждён), `protocol.published` (публикация).
**Аудит (M15):** `MEETING_PROTOCOL_ROUTE_SET`, `MEETING_PROTOCOL_SENT_FOR_APPROVAL`,
`MEETING_PROTOCOL_REWORK`, `MEETING_PROTOCOL_AGREED`, `MEETING_PROTOCOL_APPROVED`,
`MEETING_PROTOCOL_VERSION_CREATED`, `MEETING_PROTOCOL_PUBLISHED`, `MEETING_PROTOCOL_ARCHIVED`.
**Схема БД:** версия 3 — в таблицу `meetings` добавлено поле `protocol JSONB`
(миграция `MIGRATIONS[3]` применяется при старте сервера, событие TECH в M15).
Прежний вызов `meeting.approve` сохранён и работает через единый контур §2.9.

## 9. Соответствие ТЗ и принятые отклонения

- **Стек backend:** ТЗ §12 допускает «иной согласованный» стек — использован Python 3 + psycopg2
  вместо предложенного варианта; СУБД — PostgreSQL, как требует §4.1 (SQLite запрещена).
- **EXE:** собирается один автономный файл сервера (PyInstaller). PostgreSQL ставится отдельным
 официальным установщиком — объединять СУБД в один инсталлятор не требуется и не рекомендуется.
- **Инженерные расчёты (M10):** 6 методик с версионированием и проверкой диапазонов
  (бюджет радиолинии, зона покрытия, надёжность, пропускная способность, трудоёмкость ОКР,
  стоимость); формулы приведены в протоколе каждого расчёта.
- **Отчёты (M13):** HTML-снимки с печатью/PDF средствами браузера и выгрузкой HTML; табличные
  выгрузки — CSV (Excel), как предусмотрено ТЗ.
- **Клиентский рендер аналитики:** вычисляется из серверного состояния (единый владелец данных
  не нарушается); сами данные и все мутации — только на сервере.
- Демо-набор (8 пользователей, 6 проектов, 28 задач, риски, документы, расчёты, совещания)
  создаётся автоматически и служит приёмочными сценариями ТЗ.
